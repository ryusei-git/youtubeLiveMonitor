# ユーザー画面・認証・監査ログ 設計書

このアプリを「個人用の監視ツール」から「複数ユーザーが使うサービス」へ広げるための設計。
実装は本書を唯一の根拠とし、迷ったら本書の「決定事項」に従う。

## 0. 前提

| 項目 | 前提 |
|---|---|
| 想定利用者 | **信頼できる少人数**（本人・家族・友人、〜10人程度） |
| 公開範囲 | LAN または Tailscale 経由。**インターネットへの直接公開はしない** |
| 既存機能 | 管理者向けの監視・録画・通知はそのまま残す |

**この前提が変わる（不特定多数に公開する）場合、本設計のままでは不十分。**
その場合に追加で要るものは「9. 公開する場合に追加で必要なこと」に記載。

## 1. 方針

### 1.1 なぜ認証が先か

監査ログの目的は「不正防止」と「原因追及」で、どちらも**行為者を特定できて初めて成立する**。
認証の無い監査ログは「何かが起きた」しか言えず、証跡にならない。
したがって実装順序は **認証 → 監査ログ → ユーザー機能** で固定する。

### 1.2 記録の三層構造

目的が違うものを 1 か所に混ぜると、どちらの目的も達成できない。
閲覧まで全部 DB に入れると量が爆発して不正の痕跡が埋もれ、
ログファイルだけにすると検索も集計もできない。三層に分ける。

| 層 | 保存先 | 対象 | 保持 | 目的 |
|---|---|---|---|---|
| **監査ログ** | DB（`audit_logs`） | 状態変更操作＋認証の全手続き | 長期 | 不正防止 |
| アクセスログ | ファイル | 全リクエストの1行要約 | 短期 | 原因追及 |
| アプリログ | ファイル（既存） | 処理の詳細 | 短期 | 原因追及 |

### 1.3 相関ID

1 つの操作が複数のログに散るため、**リクエストごとに相関ID（`requestId`）を発行し、
三層すべてに載せる**。監査ログで不審な操作を見つけたら、同じ相関IDでアプリログを引けば
その操作中に何が起きたかを追える。

既存の `ChannelLogContext`（MDC でチャンネルIDを載せる仕組み）と同じ方式で実装する。
MDC のキーは `requestId` / `userId` を追加する。

### 1.4 監査ログは追記のみ

**更新・削除の API を作らない。** 証跡が書き換えられるなら証跡ではない。

- `AuditLogRepository` に更新系メソッドを定義しない
- **DB管理画面（`tables.html`）から `audit_logs` を除外する**
  （この画面はセルをダブルクリックして直接編集できるため、除外しないと改ざん可能）

## 3. 段階1：認証基盤

### 3.1 採用技術

`spring-boot-starter-security` を追加する。自前でセッション管理やパスワード比較を書かない
（タイミング攻撃対策・セッション固定攻撃対策などを自前で正しく書くのは現実的でない）。

```gradle
implementation 'org.springframework.boot:spring-boot-starter-security'
```

### 3.2 エンティティ `AppUser`

テーブル名は `app_users`。`users` は H2 の予約語と衝突する可能性があるため避ける。

| カラム | 型 | 制約 | 備考 |
|---|---|---|---|
| `id` | BIGINT | PK, IDENTITY | |
| `username` | VARCHAR(64) | NOT NULL, UNIQUE | ログインID |
| `password_hash` | VARCHAR(100) | NOT NULL | **BCrypt**。平文は絶対に保存しない |
| `role` | VARCHAR(16) | NOT NULL | `ADMIN` / `USER` |
| `enabled` | BOOLEAN | NOT NULL, default true | 無効化してもログは残す（削除しない） |
| `created_at` | TIMESTAMP | NOT NULL | |
| `last_login_at` | TIMESTAMP | NULL可 | |

**スキーマ上の注意（CLAUDE.md 参照、過去に事故済み）**

- `role` は enum だが **必ず `@Column(columnDefinition = "varchar(16)")` を付ける**。
  付けないと H2 のネイティブ ENUM 型になり、後から列挙子を足した瞬間に
  その列の全読み書きが壊れる（`Recording.status` で実際に発生した）
- `enabled` は boolean primitive なので **`columnDefinition = "boolean default true"`** を付ける
  （既存行がある状態での NOT NULL 追加は失敗する。`recordEnabled` で実際に発生した）

### 3.3 初期管理者の作成

起動時に管理者が 1 人もいなければ、`.env` の値から作成する。

```
ADMIN_USERNAME=admin
ADMIN_PASSWORD=（初回のみ使用）
```

- **パスワードは必ず BCrypt でハッシュ化して保存**し、`.env` の値は読み捨てる
- 作成したことを **INFO でログに残す**（いつ誰が作られたか追えるように）
- 既に管理者が居れば何もしない（起動のたびに上書きしない）

### 3.4 認可ルール

| パス | 権限 |
|---|---|
| `/login`, `/css/**`, `/js/**` | 全員 |
| `/api/auth/**` | 全員（ログイン処理自体） |
| `/tables.html`, `/api/tables/**` | **ADMIN のみ** |
| `/logs.html`, `/api/logs/**` | **ADMIN のみ** |
| `/api/settings/**` | **ADMIN のみ** |
| `/audit.html`, `/api/audit-logs/**` | **ADMIN のみ** |
| `/index.html`（ダッシュボード） | ADMIN のみ |
| その他のユーザー画面・API | 認証済みユーザー |
| `/recordings/**`（録画ファイル本体） | **認証済みユーザー**（下記参照） |

**録画ファイルの配信を認証の外に置かないこと。** `RecordingResourceConfig` が
`/recordings/**` を静的配信しているが、ここを素通しにすると
**URL を知っていれば誰でも動画を取得できる**。認証の対象に含める。

### 3.5 CLI への影響

CLI（`cli` プロファイル）は Web サーバーを起動しないため認証の対象外。
ただし **`@Profile("!cli")` を付け忘れると CLI が起動できなくなる**
（`MonitoringController` で実際に発生済み）。Security 関連の Bean は
Web 専用であることを明示すること。

### 3.6 テスト

- パスワードがハッシュ化されて保存されること（平文が DB に無いこと）
- 認証なしで保護対象パスへアクセスすると 401/302 になること
- `USER` が管理者専用パスへアクセスすると 403 になること
- 初期管理者が二重作成されないこと

## 4. 段階2：監査ログ

### 4.1 エンティティ `AuditLog`

| カラム | 型 | 制約 | 備考 |
|---|---|---|---|
| `id` | BIGINT | PK, IDENTITY | |
| `occurred_at` | TIMESTAMP | NOT NULL | |
| `request_id` | VARCHAR(36) | NULL可 | 相関ID |
| `user_id` | BIGINT | NULL可 | **FK を張らない**（下記） |
| `username` | VARCHAR(64) | NULL可 | **記録時点の名前を複写** |
| `client_ip` | VARCHAR(45) | NULL可 | IPv6 も入る長さ |
| `action` | VARCHAR(48) | NOT NULL | enum 名（`columnDefinition` 必須） |
| `target_type` | VARCHAR(32) | NULL可 | `CHANNEL` / `RECORDING` など |
| `target_id` | VARCHAR(128) | NULL可 | |
| `outcome` | VARCHAR(16) | NOT NULL | `SUCCESS` / `FAILURE`（`columnDefinition` 必須） |
| `detail` | VARCHAR(1000) | NULL可 | 失敗理由など |

**`user_id` に外部キーを張らない理由。**
ユーザーを削除したときに監査ログまで連鎖削除されたら証跡にならない。
`MonitoredChannel` と `Recording` が `ON DELETE CASCADE` になっているのとは**逆の方針**を取る。
同じ理由で `username` を複写して持つ（後からユーザーが消えても誰の操作か分かるように）。

### 4.2 記録する操作

**認証まわりは全手続き**（要望どおり）。

| action | 記録タイミング |
|---|---|
| `LOGIN_SUCCESS` / `LOGIN_FAILURE` | ログイン試行のたび |
| `LOGOUT` | ログアウト |
| `PASSWORD_CHANGE` | パスワード変更（成功・失敗とも） |
| `USER_CREATE` / `USER_DELETE` / `USER_DISABLE` | 管理者操作 |
| `ACCESS_DENIED` | 権限の無いパスへのアクセス試行 |

**状態を変える操作**。

| action | 対象 |
|---|---|
| `CHANNEL_REGISTER` / `CHANNEL_DELETE` | チャンネル |
| `CHANNEL_SETTING_CHANGE` | 録画ON/OFF、フィルター変更 |
| `DOWNLOAD_REQUEST` | URL指定ダウンロード |
| `RECORDING_DELETE` | 録画削除 |
| `NOTIFICATION_SETTING_CHANGE` | 通知設定 |
| `APP_SETTING_CHANGE` | アプリ設定（管理者） |

**閲覧操作は記録しない。** 録画 1 本の再生で Range リクエストが数十件飛ぶため、
記録すると監査ログが閲覧記録で埋まり、不正の痕跡が見えなくなる。

### 4.3 失敗を必ず記録する

**成功だけ記録する監査ログは役に立たない。**
ログイン失敗の連続は総当たり攻撃の兆候であり、権限の無い操作の試行は不正の証跡そのもの。
`outcome = FAILURE` と `detail`（理由）を必ず残す。

### 4.4 記録の実装方式

**AOP（`@Around`）や `HandlerInterceptor` で全 API を横取りする方式は採らない。**
「どの操作が何を対象にしたか」はメソッドの引数と結果を見ないと決まらず、
横取り方式だと判定が複雑になり、記録漏れや誤記録が起きやすい。

代わりに **`AuditLogger` を各サービスから明示的に呼ぶ**。
呼び忘れは起きうるが、記録内容が正確で、後から読んだときに
「ここで監査ログを残している」ことがコード上で見える利点を取る。

例外だけは横断的に拾う。`GlobalExceptionHandler` に `ACCESS_DENIED` の記録を足す。

### 4.5 記録が本処理を壊さないこと

**監査ログの記録に失敗しても、本来の処理は成功させる。**
記録できないことを理由にチャンネル登録が失敗するのは本末転倒。
`AuditLogger` の内部で例外を捕まえ、`log.error` に落として握る
（この「握る」判断は監査ログに限った例外的なもので、他ではやらない）。

ただし**握ったことは必ずアプリログに ERROR で残す**。

### 4.6 相関IDとユーザーの引き回し

`ChannelLogContext`（既存）と同じ方式で `RequestContext` を作る。

- サーブレットフィルターで `requestId`（UUID）を発行し MDC に載せる
- 認証済みなら `userId` / `username` も MDC に載せる
- レスポンスヘッダー（`X-Request-Id`）にも載せる（画面でエラー時に表示し、問い合わせに使える）
- **必ず `finally` で MDC を消す**（スレッドプール使い回しで他リクエストに漏れるため）

**ログ書式を変える場合は `ChannelLogReader.LOG_LINE_PATTERN` も直すこと**（CLAUDE.md 参照）。
相関IDはアプリログの本文の先頭に `[相関ID] ` として出す（リクエストの外の行には付けない）。
「日時 [レベル] ロガー - 」の部分は変えないので `LOG_LINE_PATTERN` は変えずに済む（`logback-spring.xml` のコメント参照）。

### 4.7 管理者向け閲覧画面

`audit.html` を追加。既存のログ画面（`logs.html`）と同じ作法で作る。

- 絞り込み：期間 / ユーザー / 操作種別 / 成否
- **選択肢は実データから作る**（`logs.html` と同じ。固定で並べると「選んだのに0件」が起きる）
- ページング（`PageResponse` を使う。`Page<T>` を直接返さない）
- **一覧のセルは折り返さない**（`white-space: nowrap`）。長い `detail` は
  `common.js` の `collapsibleCell()` を使う

## 5. 段階3〜7：ユーザー機能

### 5.1 段階3：権限分離

既存の管理者向け機能に 3.4 の認可を適用する。**ここで既存機能が壊れないことの確認が最重要。**
巡回・録画・通知はバックグラウンド処理であり、認証の影響を受けてはいけない。

### 5.2 段階4：チャンネル登録（ユーザーごと）

**「ユーザーが登録したチャンネル」と「監視対象」を分ける。**
同じチャンネルを 2 人が登録しても、巡回は 1 回で済ませたい。

```
app_users ──< user_subscriptions >── channels
                （誰が・どのチャンネルを）
```

- `channels` は従来どおり「監視対象の実体」。巡回はこの単位
- `user_subscriptions` に「ユーザーごとの設定」（通知するか・フィルター）を持つ
- **最後の購読者が解除したときに `channels` をどうするか**を決めること。
  推奨：残す（録画履歴が紐づくため）。ただし購読者ゼロのチャンネルは巡回対象から外す

### 5.3 段階5：通知（ユーザーごと）

現在 Discord Webhook はアプリ全体で 1 つ。ユーザーごとに持たせる。

- `user_subscriptions` 単位ではなく `app_users` 単位で通知先を持つのが素直
- **Webhook URL は秘密情報**。既存の設定画面と同じく、画面には「設定済み」の有無だけ返し、
  値そのものは返さない（`SettingsResponse` と同じ作法）

### 5.4 段階7：横断検索（**要方針決定**）

**ここが最大の制約。** 実測済みの事実：

| API | 消費 | 1日の上限 |
|---|---|---|
| YouTube `search.list` | **100 / 回** | 10,000 → **1日100回** |
| Twitch `/helix/search/channels` | 実質制限なし | — |

**10人で使えば 1人1日10回**。数回スクロールで枯渇する。
また YouTube だけ止まって Twitch だけ動くという非対称も起きる。

採りうる方針（実装前に決めること）:

1. **検索結果をキャッシュする**（同じ語句は一定時間 API を叩かない）
2. **ユーザーごとに1日の検索回数上限を設ける**（監査ログで超過も記録できる）
3. **検索対象を登録済みチャンネル内に限る**（API を使わない。クォータ消費ゼロ）
4. YouTube は `yt-dlp` の検索を使う（クォータ非消費。ただし非公式な手段で壊れやすい）

**推奨は 1 + 2 の併用。** 3 は「横断検索」の要件を満たさず、4 は
CLAUDE.md が戒める「公式に保証されない手段への依存」を増やす。

### 5.5 段階6：ダウンロード（ユーザーごと）

既存の URL 指定ダウンロード機能をそのまま使う。追加で必要なこと：

- **ユーザーごとのディスク使用量の上限**。無制限だと 1 人で埋め尽くせる
- ダウンロード要求を `DOWNLOAD_REQUEST` として監査ログに記録
- 誰が要求した録画かを持つ（`recordings` に `requested_by` を追加。**NULL 可**。
  既存行と巡回による自動録画は NULL）

## 6. 既存機能を壊さないための確認項目

実装のたびに必ず確認する。

- [ ] `./gradlew clean build javadoc` が**警告ゼロ**
- [ ] `npx -y -p typescript tsc -p src/main/resources/static/jsconfig.json --noEmit` が**型エラーゼロ**
- [ ] ビルド後に **`bin/service.sh restart` まで実行**
      （稼働中に jar を差し替えると動いているプロセスが壊れる。実際に発生済み）
- [ ] **巡回・録画・通知が従来どおり動く**（`POST /api/monitor/check` で確認）
- [ ] CLI が起動できる（`java -jar build/libs/*.jar channel list`）
- [ ] 録画ファイルが再生できる（認証を足した後は特に）

## 7. スキーマ変更時の必須事項（過去に3回事故している）

- enum の列は **必ず `columnDefinition = "varchar(N)"`**
  （無いと H2 ネイティブ ENUM になり、列挙子追加で全更新が壊れる）
- **boolean primitive の新規列は `columnDefinition = "boolean default false"`**
  （既存行があると NOT NULL 追加に失敗し、列が作られないまま全クエリが壊れる）
- `ddl-auto: update` は**カラムの削除・リネーム・NULL制約の変更をしない**。
  必要な場合は**手動 ALTER の手順を本書に追記**してから実施する
- **`data/` を消して作り直す判断は絶対に自分でしない**（実データが入っている）

## 8. やらないこと

- OAuth / 外部IDプロバイダ連携（少人数前提では過剰）
- パスワードリセットのメール送信（メール基盤が無い。管理者が再設定する運用）
- 監査ログの外部送信・SIEM連携
- 閲覧操作の監査記録（4.2 参照）
- 既存の管理者向け機能の作り直し（権限を被せるだけに留める）

## 9. 公開する場合に追加で必要なこと

前提（0章）が変わり、不特定多数へ公開する場合は本設計では不十分。最低限これらが要る。

- ログイン試行回数の制限とアカウントロック
- HTTPS 必須化（Cookie の `Secure` / `SameSite` 設定）
- CSRF 対策の有効化（Spring Security の既定を切らない）
- セッションの有効期限とアイドルタイムアウト
- 監査ログの保持期間と削除方針（個人情報保護の観点）
- `/tables.html`（DB直接編集）と `/playground.html` の削除検討
