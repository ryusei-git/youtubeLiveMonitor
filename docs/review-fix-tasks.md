アプリが従来どおり動くこと。** 途中で中断しても壊れた状態で残らないようにする。

影響範囲が大きい順ではなく、**独立して直せるものから**並べている。

## 方針として決めたこと

### #2 の排他（4-2）

**ライブ配信URLの手動ダウンロードは明示的に拒否する。**
手動ダウンロードは VOD（録画済み動画）向けの機能で、ライブ配信の取得は自動録画の担当、
と責務を分ける。利用者には「配信中の動画はダウンロードできません。
自動録画をご利用ください」と分かる形で伝える。

**ただし拒否だけでは不十分。** ライブ判定の時点と実際に録画が始まる時点には時間差があり、
「判定時は配信していなかったが、直後に配信が始まって自動録画が動く」経路が残る。
**両経路で同じ排他機構を共有すること**（別々の集合を互いに参照し合うのではなく、
1 つの予約機構に統合する）。

## 各タスクの完了条件（共通）

1. `./gradlew clean build javadoc` が**警告ゼロ**
2. `npx -y -p typescript tsc -p src/main/resources/static/jsconfig.json --noEmit` が**型エラーゼロ**
3. 画面ファイルや jar を変更したら **`./gradlew build -x test` の後に `bin/service.sh restart`**
4. **既存機能が壊れていないこと**を実機で確認
   - `POST /api/monitor/check` で巡回が従来どおり動く（現在 19 チャンネル。
     認証が要るので `.env` の `ADMIN_USERNAME`/`ADMIN_PASSWORD` で
     `POST /api/auth/login`。**パスワードの値は報告に書かないこと**）
   - `java -jar build/libs/*.jar channel list` で CLI が動く
5. この表の「状態」を更新し、`docs/review-fixes-for-claude.md` の該当項目にも
   対応済みである旨と**検証していない範囲**を追記する

## 4-2 の設計（着手前に確定させたもの）

### 予約機構は 1 つに統合する

`StreamRecorder.activeRecordings` と `VideoDownloadService.activeDownloads` という
**2 つの集合を残したまま互いを参照し合う形にしてはならない**。
「相手の集合を見る」→「自分の集合に入れる」の 2 操作の間に割り込む余地が残り、
同時開始の競合は防げないため（これは今回の指摘そのもの）。

**`ActiveVideoJobs`（`service` パッケージの `@Component`）に 1 つの集合を持たせ、
両サービスがそこへ予約する。** 追加が成否をその場で返す
（`ConcurrentHashMap.newKeySet().add()`）ことが排他そのものになる、という
現在の考え方はそのまま引き継ぐ。状態を持つので `util` ではない
（`util` は状態を持たない static メソッド用、CLAUDE.md 参照）。

- 予約のキーは**動画 ID**。出力先パスではない。
  同じ動画 ID なら保存先ディレクトリが違っても（自動録画は `{チャンネルID}/`、
  未紐づけの手動DLは `downloads/`）二重取得に意味は無く、
  `RecordingReconciler` が問い合わせるキーとも揃う
- `RecordingReconciler` の 1 段目の判定は、この 1 か所への問い合わせに置き換えてよい
  （`isRecording` と `isDownloading` の論理和と等価）。**2 段階判定そのものは絶対に残す**
  ——OS 上のプロセス確認（`ProcessLauncher.isRunningWithCommandLineContaining`）を
  外すと、再起動直後にまだ生きている録画を失敗と誤判定する（CLAUDE.md 参照）

### ライブ配信 URL の手動ダウンロードは拒否する

`VideoSource` に `yt-dlp` の `live_status` を足して判定する。
`PRINT_TEMPLATE` と `parse()` は**対になっているので必ず同時に直す**
（片方だけ変えると値が 1 つずつずれるという分かりにくい形で壊れる。`VideoSource` の JavaDoc 参照）。
**自由入力であるタイトルは末尾のまま**にすること（`|` を含むタイトルがあるため）。

- 拒否するのは `is_live` と `is_upcoming`。専用の例外を作り、
  `GlobalExceptionHandler` で 400 として「配信中の動画はダウンロードできません。
  自動録画をご利用ください」と返す
- `post_live`（配信直後でまだ処理中）と `was_live` は**拒否しない**。
  これらは既に配信が終わっており、自動録画と重なる場合は予約機構が弾くのが正しい層
- 画面（`recordings.js`）は API のメッセージをそのまま出していれば追加対応は不要。
  そうなっていない場合だけ直す

### 起動済みプロセスを取り残さない（#4）

`processLauncher.launch()` の**後**、完了待ちの仮想スレッドを起動する**前**に例外が出る経路
（`recordingHistoryService.recordStart()` の DB 障害・外部キー違反など）では、
起動済みの `yt-dlp` を止めてから例外を投げ直す。止めずに予約だけ外すと、
次の巡回で同じ出力先に別プロセスが起動する。

- **`destroyForcibly()` を呼ぶだけで終わりにしない。** 実際に終了したことを確認してから
  予約を外す。確認前に外すと、まだ出力先に書いているプロセスと次の起動が重なる
- 終了処理は `ExternalCommandRunner` に同じものが既にあるので、
  **`util` に stateless な独立クラスとして切り出して両者で使う**（CLAUDE.md の方針）。
  ただし `ExternalCommandRunner` の**挙動と既存テストは変えないこと**
  （タスク 4-1 で検証済みの箇所なので、リファクタで壊さない）
