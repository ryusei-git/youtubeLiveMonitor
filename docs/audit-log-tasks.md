# 段階2：監査ログ — タスク分割と進捗

設計の根拠は `docs/user-portal-design.md` の 4 章。本書は**実行単位と進捗**だけを管理する。

## 分割の原則

**各タスクは、終わった時点で `./gradlew clean build javadoc` が警告ゼロで通り、
アプリが従来どおり動くこと。** 途中で中断しても壊れた状態で残らないようにするため、
「新規追加だけのタスク」を先に、「既存コードを変更するタスク」を後に置く。

## 進捗

| # | タスク | 既存への影響 | 状態 |
|---|---|---|---|
| 2-1 | `AuditLog` エンティティ・enum・リポジトリ／DB管理画面から `audit_logs` を除外 | なし（追加のみ） | 完了 |
| 2-2 | 相関ID（`RequestContext`）のフィルター | なし（追加のみ） | 完了 |
| 2-3 | `AuditLogger` と認証イベントの記録 | 認証ハンドラを変更 | 完了 |
| 2-4 | 状態変更操作の記録＋`ACCESS_DENIED` | 各サービスを変更 | 一部完了（利用者管理・招待・チャンネル登録削除・購読） |
| 2-5 | 管理者向け監査ログ閲覧画面 | 追加のみ | 未着手 |

**完了したタスクは、担当したエージェントがこの表の「状態」を「完了」に更新すること。**

## 各タスクの完了条件（共通）

1. `./gradlew clean build javadoc` が**警告ゼロ**
2. `npx -y -p typescript tsc -p src/main/resources/static/jsconfig.json --noEmit` が**型エラーゼロ**
3. 画面ファイルや jar を変更したら **`./gradlew build -x test` の後に `bin/service.sh restart`**
   （稼働中に jar を差し替えると動いているプロセスが壊れる。実際に発生済み）
4. **既存機能が壊れていないこと**を実機で確認
   - `java -jar build/libs/*.jar channel list` で CLI が動く
   - ログイン後に既存画面が従来どおり見える
   - 定期巡回がログに出ている
5. この表の「状態」を更新する

## 触ってはいけないもの

- `data/`（実データが入っている。手動 ALTER が必要なら**実行せず報告**）
- `.env`（管理者パスワードが入っている）
- `recordings/` の既存ファイル
