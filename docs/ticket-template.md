# Issue の書き方

Issue は実装担当への**唯一の指示書**。実装担当は会話履歴を持たず、Issue 本文と
作業ツリーだけで作業する。Codex は軽量モデル（gpt-6-luna）で動かしているため、
**判断の余地を残すほど外れる**。「何を」だけでなく「どこを・どう・何をしないか」まで書く。

## 担当の決め方

次のどれかに当てはまるものは **Claude が担当**する。それ以外は Codex。

- 原因が分かっていない不具合の調査
- 認証・権限・セキュリティに関わる変更
- DB のスキーマ変更（カラム追加・型変更）
- 並行処理・外部プロセス（巡回の排他、yt-dlp、録画の後始末）
- 設計判断が要る変更、既存に真似できる実装が無い変更
- 変更するファイルを事前に列挙できないもの

Codex に渡すものは、**変更するファイルとメソッドを列挙でき、真似できる既存実装がある**ことを目安にする。
列挙できないなら、調査を Claude が先に済ませてから切り出す。

## テンプレート

```markdown
担当: Codex

## 目的
<なぜこの変更が要るか。1〜3 行>

## 変更するファイル
- `src/main/java/.../Foo.java` — `bar()` に〇〇を追加
- `src/main/resources/static/js/baz.js` — `qux()` の〇〇を変更

## 手順
1. <具体的な操作。メソッド名・引数・戻り値・文言まで書く。場所は行番号でなく探す文字列で示す>
2. ...

## 真似する既存実装
- `src/main/java/.../Similar.java` の `method()`（同じパターン）

## 使う既存の部品
- `src/main/java/.../util/Helper.java` の `helper()`（同じ処理を書き直さずに呼ぶ）

## やらないこと
- <範囲外にしておくこと。手を出しやすい周辺の改修を明示的に禁じる>

## 関連する落とし穴
- `docs/pitfalls.md`「<項目名>」

## 同時に起きること・途中の失敗・停止
- 同時: <同じ操作が重なったとき（2 回押す・巡回と画面の操作・2 人が同時に）どうなるべきか>
- 途中の失敗: <途中で例外・時間切れになったとき、画面の表示・DB の行・ファイルに何を残し何を戻すか>
- 停止: <止めた・再起動したときに、待っているスレッド・外部プロセスがどうなるべきか>

## 完了条件
- AGENTS.md「終わったら」の共通確認
- <この Issue 固有の確認。コマンドと期待される結果を書く>
  例: `ENV_FILE=.sandbox/.env SERVER_PORT=<割り当てられたポート> bin/api.sh GET /api/foo` が
  `{"bar": ...}` を返す
```

## 書くときの注意

- **ファイルパス・メソッド名は実在を確かめてから書く。** 存在しない名前を書くと、
  実装担当はそれを作り始める。
- **1 Issue ＝ 1 コミットで終わる大きさ**にする。変更ファイルが 4 つを超えるならサブイシューに割る。
- 画面の文言・API の JSON のように**正解が 1 つに決まるものは、そのまま書く**。
- **完了条件は、実際に満たせることを確かめてから書く。** ログに出ない情報（書式に無いスレッド名、DEBUG の行）や、
  コードを変えなくても毎回変わる値（`lastObservedAt` など）を比べる diff は完了条件にならない（実際に発生した）。
- **完了条件にポート番号と `origin/main` を書かない。** ポートは「割り当てられたポート」
  （AGENTS.md「終わったら」）、差分を比べる相手は「PR のベースブランチ」と書く。
- **場所は行番号でなく、探す文字列（アンカー）で示す。** 例: 「`if (foo.isBar())` の直前に」。
  行番号は、ほかの PR が先に入るとずれる。探す文字列は、そのファイルに 1 回だけ出るものを選ぶ。
- **呼び出し元の一覧や個数を書かない。** 書いた後に入った PR で変わり、JavaDoc に写されて実際と
  食い違う。要るなら探し方（`grep -rn "foo(" src/main/java`）を書く。
- **Issue に載せる JavaDoc の文面は、約 100 桁（全角は 2 桁）で折り返しておく。** 1 行で載せると、
  そのまま長い 1 行で写される。
- **Issue に載せるコードは、ライブラリ・JDK の実際の挙動を確かめてから書く。** 投げる例外の型や
  受け付ける引数の形が、試作と違っていた（実際に発生した）。見えない文字は `\u` で書かず（写すときに
  生の文字へ展開された）、`Character.getType()` のような名前の付いた判定にする。
- **振る舞いを変える Issue は、README の該当する節も「変更するファイル」に入れる。**
- **「同時に起きること・途中の失敗・停止」は、書く側が先に洗い出す。** 当てはまらない行も消さず、
  「なし（<理由>）」と書く。
- **「使う既存の部品」には、手順で呼ぶ util・`common.js` の関数を挙げる。** 挙げないと、同じ処理を
  書き直される（実際に発生した）。
- **「〇〇の後に着手」と書く前に、待ち合わせ先の Issue がまだオープンかを確かめる。**
  クローズ済みの #178 を待たせる記述が複数あった。
- **同じファイルを触る Issue が他にあれば、本文に順序を書く。** `gh issue list --search <ファイル名>` で探す
  （`bin/service.sh` を 4 件が同時に触っていた）。
- 作成は `bin/create-issue.sh <title> <body-file> [親issue番号] [P1|P2]`。本文はファイルで渡す。
