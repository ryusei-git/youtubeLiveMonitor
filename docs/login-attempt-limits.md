# ログイン試行の回数制限（Issue #3）

`POST /api/auth/login` の認証前に、利用者名と接続元IPの両方で制限する。

| 単位 | 失敗回数の上限 | 制限期間 |
| --- | --- | --- |
| 利用者名 | 5回 | 上限到達から15分 |
| 接続元IP | 20回 | 上限到達から15分 |

- 上限回数までの失敗は従来のログインエラー。次の試行からHTTP 429と `Retry-After`（秒）を返し、ログイン画面へ戻るリンクを表示する。制限中は正しいパスワードでも照合へ進めない。
- 利用者名の存在確認は制限判定で行わない。未登録・登録済みとも同じ回数で同じ応答となる。
- 利用者名の前後の空白を除く処理をSpring Securityの認証処理と揃える。名前は大文字小文字を区別する。
- 成功時は、その利用者名と接続元IPの両方の連続失敗をリセットする。上限に届かない失敗記録も15分で期限切れになる。
- 認証中の件数も枠として予約し、同時送信で上限を超えて照合させない。枠は例外時も解放する。認証中の枠だけで上限に達した場合は `Retry-After: 1`。
- 制限中の再送では失敗回数を増やさず、停止期限も延長しない。
- 利用者名・IPの各記録を最大10,000件に制限する。期限内の記録を追い出して制限を回避されないよう、容量到達時は新しいキーの認証を429で拒否し、60秒後の再試行を案内する。

## 運用上の範囲

記録は単一JVMのメモリ内に保持し、再起動でリセットされる。複数インスタンス間の共有や永続化は今回の対象外。

接続元は `request.getRemoteAddr()` を使い、任意の `X-Forwarded-For` / `Forwarded` を自前では信頼しない。現在の構成ではプロキシ経由の利用者はプロキシのIPとして集計される。転送ヘッダーを有効化する場合は、信頼できるプロキシからの接続に限定するネットワーク設定が必要。

管理者も同じ制限の対象。既にログイン済みのセッションや、ログイン以外の画面・APIにはこの回数制限を掛けない。本番利用者のパスワードを誤入力して検証することは避ける。

## 検証

- `JAVA_TOOL_OPTIONS=-Xshare:off ./gradlew clean build javadoc`：既存607テスト成功、警告0。JVMクラス共有の設定は検証時のみ。本番JVM設定は変更しない。
- `tsc --noEmit`：型エラー0。テストファイルの新規作成・変更は行っていない。
- 一時ディレクトリの時刻制御付き確認プログラムで、利用者名/IPの上限、15分後の解除、成功時リセット、50件同時送信で許可5件、10,000件の容量制限を確認。
- 別プロセス・インメモリH2で、成功を挟む連続失敗のリセット、登録済み/未登録の同一429、停止中の正しいパスワード拒否、名前と転送ヘッダーを変えてもIP制限が続くことを確認。
- 実ブラウザの390px幅で制限画面とログイン画面への復帰を確認。
- ビルド後にサービスを再起動。手動巡回は `checkedChannels: 20`、CLI `channel list` は終了コード0。
