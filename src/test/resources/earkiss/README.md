# 耳キスの検出器の突き合わせ用データ（ear-kiss-fixture-v1）

Java の検出器（ear-kiss-linear12-v1）が、Python の参照実装と同じ値を出すことを JUnit で確かめるためのデータ。
仕様は Issue #466 の結論のコメントにある。Issue #465 の決まりに従い、中身は合成した音だけで、配信の音声は入っていない。

## ファイル

| ファイル | 中身 | リポジトリでの置き場所（案） |
|---|---|---|
| `ear-kiss-fixture.pcm` | 合成した音（20 秒） | `src/test/resources/earkiss/` |
| `ear-kiss-fixture-expected.json` | 参照実装がこの PCM から出した値 | `src/test/resources/earkiss/` |
| `README.md` | この説明 | `src/test/resources/earkiss/` |

期待値の `logit`・`p`・`segments`・`final` は、重みのファイル `ear-kiss-linear12-v1.json`（`src/main/resources` に置くもの。Issue #466 のコメントに全文がある）で計算してある。
重みを変えて版を上げたら、この 4 つは作り直す（参照実装は Issue #466 の結論のコメントの次のコメントにある）。

## PCM の形式

- ヘッダーのない生の PCM。16bit 符号付き整数・リトルエンディアン・2ch（左・右の順に 1 サンプルずつ交互）・32000Hz。
- 1ch あたり 640000 サンプル（20.000 秒）、2,560,000 バイト。
- sha256: `4f2af3d4e91f8078d55ea1603e310b93986f8e173b1c3fb1c3b502398eb2c69a`
- 本番で ffmpeg の標準出力から読むバイト列と同じ形。テストでは ffmpeg を通さず、このファイルのバイト列を検出器の入力にする。
  値は `short / 32768.0`。

## 期待値 JSON の形式

フレームの番号はどれも録音の先頭から数える。帯域フレーム p は 5ms ごと（窓 = サンプル 160p〜160p+511）、
細かいフレーム q は 1ms ごと（窓 = サンプル 32q〜32q+63）。耳は 0 = 左、1 = 右。

| 項目 | 型 | 中身 |
|---|---|---|
| `fixture` | 文字列 | `ear-kiss-fixture-v1` |
| `model` | 文字列 | 期待値の計算に使った重みの版（`ear-kiss-linear12-v1`） |
| `pcm` | オブジェクト | 上の PCM の形式と sha256 |
| `tolerance.real` | 実数 | 実数を比べるときの絶対誤差（`1e-9`） |
| `bandFrames` | 整数 | 帯域フレームの数 T（3997） |
| `fineFrames` | 整数 | 細かいフレームの数 Q（19999） |
| `bgBlocks` | 実数の配列 | 100 フレームごとのブロックの背景（20 パーセンタイルの 5 ブロック中央値）。ブロック j がフレーム 100j〜100j+99 の背景。40 個 |
| `onsets` | 整数の配列 | 立ち上がりの条件を満たしたフレーム t（つなぐ前）。確かめ用 |
| `candidates` | 配列 | 候補（40ms 以内をつないで、最初と最後の 0.5 秒を除いた後）。フレームの小さい順。1 件 = `frame`・`D`・`bg` |
| `majors` | 配列 | 目立つ候補。フレームの小さい順。下の表 |
| `segments` | 配列 | p ≥ 0.7 の目立つ候補をつないだ区間すべて。下の表 |
| `final` | 配列 | 最終の候補（時刻順）。下の表 |

`majors` の 1 件:

| 項目 | 型 | 中身 |
|---|---|---|
| `frame` | 整数 | 山の帯域フレーム p |
| `timeSec` | 実数 | `frame / 200.0` |
| `ear` | 整数 | 大きい方の耳 c |
| `features` | オブジェクト | 12 特徴（重みのファイルと同じ順・同じ名前。切り詰めた後の値） |
| `logit`・`p` | 実数 | 線形モデルの出力と、その確率 |
| `debug.hfL`・`debug.hfR` | 実数 | 山のフレームの左右の hf（1〜16kHz の dB） |
| `debug.bg` | 実数 | 山のフレームの背景 |
| `debug.fineQ0` | 整数 | `5 × frame + 8` |
| `debug.finePeak` | 整数 | 耳 c の E の、`fineQ0−10`〜`fineQ0+34` での最大の位置 q（同じ値なら先） |
| `debug.fineTop` | 整数 | その位置の E |
| `debug.burstFirst`・`debug.burstLast` | 整数 | `finePeak−30`〜`finePeak+119` で E ≥ `fineTop−12` だった最初と最後の q（破裂の範囲） |
| `debug.subPeaks` | 整数の配列 | nsub を数えるのに使った小さな山の q |

`segments` の 1 件: `startFrame`・`endFrame`（区間の最初と最後の目立つ候補）、`count`（つながった数）、
`bestFrame`・`bestP`（p が最大の目立つ候補。同じ値なら先）、`enoughEvents`（count ≥ 2）、`kept`（上限で外されずに最終の候補に残った）。

`final` の 1 件: `frame`・`timeSec`・`ear`・`p`（代表の目立つ候補）、`count`・`startFrame`・`endFrame`（その区間）。

## 比べ方

- 整数（`bandFrames`・`fineFrames`・`onsets`・各 `frame`・`ear`・`count`・`enoughEvents`・`kept`・`debug` の q と `fineTop`・`subPeaks`）は完全に一致させる。
  配列は数と並びも一致させる。
- 実数（`bgBlocks`・`D`・`bg`・`hfL`・`hfR`・12 特徴・`logit`・`p`・`bestP`）は、絶対誤差 `1e-9` 以内。
  - Java で素直に書く基数 2 の FFT（double。#460 の `KissBench.java` と同じ手順を、同じ演算の順で Python に写したもの）と参照実装の差は、この PCM で最大 9.4e-13（`bgBlocks`）・3.5e-13（特徴）・1.0e-15（p）だった。
  - FFT を float で計算すると 1e-7〜1e-6 ずれる。`1e-9` なら、float を使ったことも見つかる。
- `timeSec` は `frame / 200.0` なので比べなくてよい（比べるならフレームで）。
- この PCM では、どの判定もしきい値から十分離れている（double の計算の差でほかの分かれ道に進まない）。いちばん近いもの:
  立ち上がりの判定 0.0149dB（フレーム 541、背景との差 9.985dB で候補にならない）、E の丸め前の値と .5 の距離 1.3e-4、
  p と 0.7 の差 0.131、区間の中の p の 1 位と 2 位の差 0.0101、上限で残す区間と外す区間の p の差 0.00368。

## 音の中身（通す分かれ道）

背景: 左右で別の白色雑音（振幅の標準偏差 1.6e-4 → 2.6e-4 にだんだん大きくなる。右は 1.1 倍）と、60・120・180Hz のうなり（ずっと鳴る）。
「山」は参照実装が出した山の帯域フレーム。

| 秒 | 山 | 耳 | 音 | 確かめること |
|---:|---:|---|---|---|
| 0.49 / 0.52 | 96 / 102 | 左 | 高い音のクリック（大→小） | 40ms 以内でつないでから、最初の 0.5 秒を除く（先に除くと 102 が候補に残る） |
| 1.00 | 200 | 右 | 耳キスらしい破裂 | p ≥ 0.7 だが 5 秒以内にほかがない単独 → 出さない（`enoughEvents` = false） |
| 1.66 | 330 | 右 | 低い音の強い叩く音（170Hz） | p が低い。`j0` が上限 40 |
| 2.16 / 2.18 | 430 / 435 | 左 | クリック（小→大） | 40ms 以内の 2 つ: 後ろが大きいので置き換える |
| 2.71 / 2.73 | 540 / 545 | 右 | クリック（大→小） | 40ms 以内の 2 つ: 後ろが小さいので捨てる |
| 3.01 | 601 | 左 | 小さいクリック | 候補だが目立つ候補ではない。1201 の ±600 フレームのちょうど端（入る） |

| 3.91 / 4.21 / 4.51 | 780 / 841 / 901 | 左 / 左 / 右 | クリック（中・大・中） | 841 から 61 フレームの 780 は目立つ候補、ちょうど 60 フレームの 901 は外れる。841 は左右がほぼ同じ（`ild` 1.2） |
| 4.75〜5.75 | − | 左 | ゆっくり大きくなる雑音 | 背景との差は 45dB まで上がるが、立ち上がりが 3.7dB 以下 → 候補にならない |

| 8.01 | 1600 | 左 | クリック＋直後の 600〜800Hz の声 | `mf_after` が上限 5（声は 1kHz 未満なので D に出ない） |
| 8.81 | 1760 | 左だけ | 耳キスらしい破裂 | `ild` が上限 30 |
| 9.02 | 1802 | 左 | 小さいクリック | 1201 から 601 フレーム → 1201 の ±600 に入らない |
| 11.48 | 2300 | 左 | 弱いクリック → 28ms 後に同じクリック 2 つ（5ms 差） | E の最大が同じ値で 2 か所 → 先の方を山にする（後ろにすると `fill` が変わる） |
| 11.90〜12.62 | − | 右 | 3〜5.5kHz の笛（ゆっくり上がって、急に止まる） | 次の音の帯域 7・8 の背景を上げる |
| 12.67 | 2532 | 右 | 9〜15kHz の短い雑音 | 帯域 7・8 の増え分が 0 → `s3` が 1e-12 の床（−132）。`j3` が下限 −10 |
| 13.80 | 2760 | 右 | 耳キスらしい破裂 | 1760 からちょうど 1000 フレーム → つながる。±3 秒の候補が 3 つ（差が 2 つ）→ `ioi_cv` = 1.0 |

2 個以上の区間 A（代表 1490・p 0.9754）と B（代表 3860・p 0.9791）のうち、p の高い B だけが残る（時刻の早い順に残すと A になる）。

## 分かれ道を通っているかの確かめ

参照実装に、移植でやりがちな誤りを 1 つずつ入れて、上の比べ方で比べた（38 通り）。32 通りで食い違いが出る。
出なかった 6 通りは、どれも「連続の値がちょうど等しいとき」か「T が 100 の倍数のとき」にしか結果が変わらないもの
（40ms 以内の 2 つが同じ高さ・t〜t+4 に同じ高さ・左右の hf が同じ・立ち上がりがちょうど 6dB・E の丸め前がちょうど .5・
ブロックの数を試作と同じ `T/100+1` にする）。これらは Issue #466 の仕様に書いてある決まりに従う。
