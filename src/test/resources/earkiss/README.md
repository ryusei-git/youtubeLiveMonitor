# 耳キスの検出器の突き合わせ用データ（ear-kiss-fixture-v2）

Java の検出器（ear-kiss-linear12-v2）が、Python の参照実装と同じ値を出すことを JUnit で確かめるためのデータ。
仕様は Issue #480 の結論のコメント（v1 の Issue #466 の「4.」への差分）にある。中身は合成した音と、手で決めた数だけで、配信の音声は入っていない。

v1（ear-kiss-fixture-v1）からの変更:
- PCM を作り直した（20 秒 → 26 秒）。v1 の音はすべて同じ役割で残し、v2 の「大きさの門」の分かれ道を通す音を足した。
  **PCM が変わったので、v1 の部分（背景・候補・目立つ候補・特徴・p）の期待値もすべて変わっている。**
- 期待値の JSON に `loudnessRef`・区間の `G`・`loudestFrame`・`passedGate`・最終の候補の `G` を足した。
- 「選び方の表」（`ear-kiss-selection-cases.json`）を足した。音では作れない「ちょうどの値」の分かれ道を、目立つ候補の値を直接与えて確かめる。

期待値は、重みのファイル `ear-kiss-linear12-v2.json`（`src/main/resources/sound/` に置くもの。Issue #480 のコメントに全文がある）で計算してある。
重みか仕様を変えたら、参照実装（Issue #480 のコメントに全文がある）で作り直す。**テストが落ちたときに、検出器が出した値で期待値を書き換えない。**

## PCM の形式

- ヘッダーのない生の PCM。16bit 符号付き整数・リトルエンディアン・2ch（左・右の順に 1 サンプルずつ交互）・32000Hz。
- 1ch あたり 832000 サンプル（26.000 秒）、3,328,000 バイト。
- sha256: `f627ea3adcca5eb06eba7b53ca41e96c1bbb3d38608f63d4e6d7162f584403ae`
- テストでは ffmpeg を通さず、このファイルのバイト列を検出器の入力にする。値は `short / 32768.0`。

## 期待値 JSON（ear-kiss-fixture-expected.json）の形式

フレームの番号はどれも録音の先頭から数える。帯域フレーム p は 5ms ごと（窓 = サンプル 160p〜160p+511）、
細かいフレーム q は 1ms ごと（窓 = サンプル 32q〜32q+63）。耳は 0 = 左、1 = 右。**太字**が v1 から足した項目。

| 項目 | 型 | 中身 |
|---|---|---|
| `fixture` | 文字列 | `ear-kiss-fixture-v2` |
| `model` | 文字列 | 期待値の計算に使った重みの版（`ear-kiss-linear12-v2`） |
| `pcm` | オブジェクト | 上の PCM の形式と sha256 |
| `tolerance.real` | 実数 | 実数を比べるときの絶対誤差（`1e-9`） |
| `bandFrames` | 整数 | 帯域フレームの数 T（5197） |
| `fineFrames` | 整数 | 細かいフレームの数 Q（25999） |
| `bgBlocks` | 実数の配列 | 100 フレームごとのブロックの背景。52 個 |
| `onsets` | 整数の配列 | 立ち上がりの条件を満たしたフレーム t（つなぐ前）。93 個 |
| `candidates` | 配列 | 候補（`frame`・`D`・`bg`）。28 個 |
| `majors` | 配列 | 目立つ候補（v1 と同じ形）。21 個 |
| **`loudnessRef`** | 実数 | 大きさの基準 ref（全目立つ候補の D の 99 パーセント点）。目立つ候補が 0 個なら `null` |
| `segments` | 配列 | p ≥ 0.7 の目立つ候補をつないだ区間すべて（時刻順）。下の表 |
| `final` | 配列 | 最終の候補（時刻順）。下の表 |

`majors` の 1 件は v1 と同じ（`frame`・`timeSec`・`ear`・`features`（12 特徴）・`logit`・`p`・`debug`（`hfL`・`hfR`・`bg`・`fineQ0`・`finePeak`・`fineTop`・`burstFirst`・`burstLast`・`subPeaks`））。
目立つ候補の D は `max(debug.hfL, debug.hfR)`（`candidates` の同じフレームの `D` と同じ値）。

`segments` の 1 件:

| 項目 | 型 | 中身 |
|---|---|---|
| `startFrame`・`endFrame` | 整数 | 区間の最初と最後の目立つ候補 |
| `count` | 整数 | つながった数 |
| `bestFrame`・`bestP` | 整数・実数 | 代表（p が最大の目立つ候補。同じ値なら先） |
| `enoughEvents` | 真偽 | count ≥ 2 |
| **`G`** | 実数 | 代表の ±400 フレーム（両端を含む）の目立つ候補（p に関わらずすべて）の D の最大 − `loudnessRef`（dB）。1 個だけの区間でも求める |
| **`loudestFrame`** | 整数 | その最大の目立つ候補のフレーム（同じ D なら先） |
| **`passedGate`** | 真偽 | G ≥ −10.0 |
| `kept` | 真偽 | enoughEvents かつ passedGate で、上限（G の高い順）で外されずに最終の候補に残った |

`final` の 1 件: `frame`・`timeSec`・`ear`・`p`（代表の目立つ候補）、**`G`**、`count`・`startFrame`・`endFrame`（その区間）。

## 選び方の表（ear-kiss-selection-cases.json）の形式

音を通さず、目立つ候補の値を直接与えて「区間・G・門・上限」だけを確かめる。
Java では、選び方（区間 → 代表 → ref → G → 門 → 上限）を「目立つ候補の（frame・ear・p・D）の列と T」だけを受け取る関数にしておき、
`majors` をそのまま入れて、出力を `loudnessRef`・`segments`・`final` と比べる。

| 項目 | 中身 |
|---|---|
| `fixture`・`model`・`tolerance` | `ear-kiss-selection-v2`・`ear-kiss-linear12-v2`・上と同じ |
| `cases[].name`・`about` | 場合の名前と、確かめること |
| `cases[].bandFrames` | T（上限 `(40 × T + 719999) / 720000` にだけ使う） |
| `cases[].majors` | 目立つ候補（時刻順）。1 件 = `frame`・`ear`・`p`・`D` |
| `cases[].loudnessRef`・`segments`・`final` | 期待値（上の期待値 JSON と同じ形。`final` に `timeSec` は無い） |

| 名前 | 確かめること |
|---|---|
| `gate-exact` | G がちょうど −10.0 の区間は門を通り、−10.0009765625 の区間は落ちる（`>=`）。上 2 つの D が同じ 50.0 なので ref = 50.0 ちょうど |
| `cap-tie` | 上限 1 件で、G が同じ（−5.0）2 区間は代表のフレームが先の方を残す（p が高い後ろではない）。p が最大の区間は G が低いので残らない。窓の中の D の最大が同じ値で 2 つあるときは先のフレームを `loudestFrame` にする |
| `cap-gate-order` | 上限 2 件。門に落ちた区間は上限の枠を使わない。G の高い 2 つを残し、時刻順に出す（G の順ではない） |
| `gate-limit` | 上限 2 件で門を通るのが 1 区間だけ: 門に落ちた区間（p は高い）は、上限に空きがあっても出さない |
| `rep-tie-window` | 区間の代表は p が同じなら先。G の窓は代表を中心に、ちょうど 400 前（600）は入り、401 後（1401）は入らない |
| `threshold-exact` | p がちょうど 0.7 はつなぎ、0.6999999999999999 はつながない（間にあっても区間を切らない）。つなぐ間隔は直前の p ≥ 0.7 から測る |
| `one-major` | 目立つ候補が 1 個: ref = その D。区間は 1 個だけなので出さない（G = 0.0 は求める） |
| `no-major` | 目立つ候補が 0 個: ref は無い（`null`）。区間も最終の候補も無い |
| `two-majors` | 目立つ候補が 2 個: ref = 20 + 0.99 × (30 − 20) = 29.9 |
| `n102` | 目立つ候補が 102 個（D = 0〜101）: pos = 99.99 で、ref は上の 2 つの間ではなく 99 と 100 の間（99.99） |

## 比べ方

- 整数（フレーム・耳・数・`debug` の q と `fineTop`・`subPeaks`・`loudestFrame`）と真偽（`enoughEvents`・`passedGate`・`kept`）は完全に一致させる。配列は数と並びも一致させる。
- 実数（`bgBlocks`・`D`・`bg`・`hfL`・`hfR`・12 特徴・`logit`・`p`・`bestP`・`loudnessRef`・`G`）は、絶対誤差 `1e-9` 以内。
  - Java で素直に書く基数 2 の FFT（double）を、同じ演算の順で Python に写したものと参照実装の差は、この PCM で最大
    1.8e-13（`bgBlocks`）・3.0e-12（特徴）・1.7e-15（p）・2.1e-14（`loudnessRef`・`G`）だった。
  - リポジトリの v1 の Java の検出器に、仕様どおりに Java で書いた v2 の選び方を足して通すと、差は最大 2.6e-13（特徴）・0（`loudnessRef`・`G`）だった。
  - FFT を float で計算すると `loudnessRef` が 1.4e-8・`G` が 4.6e-8・特徴が 2.7e-4 ずれる。`1e-9` なら float を使ったことも見つかる。
- `loudnessRef` が `null` のとき（`no-major`）は、Java 側が「無い」（例: `Double.NaN`）であることを確かめる。
- `timeSec` は `frame / 200.0` なので比べなくてよい。
- この PCM では、どの判定もしきい値から十分離れている（double の計算の差でほかの分かれ道に進まない）。いちばん近いもの:
  立ち上がりの判定 0.228dB（フレーム 541、背景との差 10.228dB）、E の丸め前の値と .5 の距離 1.2e-4、p と 0.7 の差 0.136、
  区間の中の p の 1 位と 2 位の差 0.0046、**G と −10dB の差 2.22、上限で残す区間と外す区間の G の差 1.91、
  ref の補間の 2 つの値の差 1.88、G の窓の中の D の 1 位と 2 位の差 6.17**。
- 選び方の表の値は 2 進数で割り切れる数にしてあり、ref と G の多くは丸めなしで決まる（`gate-exact` の G は −10.0 ちょうど）。

## 分かれ道を通っているかの確かめ

参照実装に、移植でやりがちな誤りを 1 つずつ入れて、上の比べ方で比べた（`kiss/ref2/mutants.py`）。

- v2 の誤り 39 通り: 37 通りで食い違いが出る（PCM で 30 通り、残り 7 通りは選び方の表で）。
  出ない 2 通りは誤りではないもの（「上限を G の順で選んでから門を掛ける」は同じ結果になる。「ref を numpy の既定の書き方で計算する」は最後の 1 桁しか違わない）。
- v1 の誤り 39 通り（#466 の 38 通りから「上限を時刻の早い順に残す」を v2 の側へ移し、2 通り足した）: 33 通りで食い違いが出る。
  出ない 6 通りは #466 と同じ（どれも「連続の値がちょうど等しいとき」か「T が 100 の倍数のとき」にしか結果が変わらない:
  40ms 以内の 2 つが同じ高さ・t〜t+4 に同じ高さ・左右の hf が同じ・立ち上がりがちょうど 6dB・E の丸め前がちょうど .5・
  ブロックの数を試作と同じ `T/100+1` にする）。これらは Issue #466 の仕様に書いてある決まりに従う。
  足した 2 通り（「区間の代表で、同じ p なら後ろ」「p のしきい値を > で（ちょうど 0.7 をつながない）」）は、選び方の表で見つかる。
- 誤りではない「FFT を Java と同じ基数 2・double で」は、どの値も 1e-9 の中に収まる（上の「比べ方」）。
